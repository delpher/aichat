# Інструкції для агентів

## Релізи

Релізи публікує `.github/workflows/release.yml` автоматично, коли в репозиторій пушиться тег версії. Вручну реліз у GitHub не створюй і файли до нього не завантажуй.

### Як випустити версію

1. Реліз робиться лише з `master` і лише з дозволу Алексея: тег і реліз публічні для апдейтера брокера, відкотити їх без наслідків не можна.
2. На актуальному `master` з чистим робочим деревом:
   ```bash
   npm run typecheck && npm test && npm run test:web
   npm version <patch|minor|major|X.Y.Z>   # міняє package.json і package-lock.json, робить коміт і тег vX.Y.Z
   git push origin master --follow-tags
   ```
   Без командного рядка: змерж PR зі зміною версії, потім Actions → «Release» → «Run workflow» на `master`. Workflow залишить чернетку релізу з файлами; Алексей публікує її в Releases, створюючи тег `v<версія>`. Сам workflow (і хмарна сесія) теги створювати не може. Тег ніколи не видаляй: видалене ім'я тегу GitHub більше не створить.
   Якщо `master` захищений від прямого пушу, зміни версію через PR (`npm version X.Y.Z --no-git-tag-version`), а після мержу постав тег на коміт мержу: `git tag vX.Y.Z <sha> && git push origin vX.Y.Z`.
3. Простеж за запуском workflow «Release» в Actions. Якщо він впав, виправ причину в новому коміті й випусти наступну patch-версію. Не перевикористовуй і не переставляй уже запушений тег.

### Правила версій

- Semver. Тег завжди `v` + версія з `package.json` (`v0.2.0`). Workflow зупиняється, якщо вони різняться.
- `patch` для виправлень, `minor` для нових можливостей, `major` для несумісних змін протоколу, API або формату `agents.json` чи бази.
- Тег із суфіксом (`v0.2.0-rc.1`) стає пре-релізом: `/releases/latest` його пропускає, Docker-тег `latest` не ставиться. Ним перевіряй ризиковані зміни.

### Що не можна ламати

Брокер оновлюватиметься сам із GitHub Releases, тому ці речі є контрактом. Змінюєш їх, то онови апдейтер і README у тому ж PR:

- імена файлів у релізі: `aichat-<версія>.zip`, `aichat-<версія>.tar.gz`, `SHA256SUMS.txt`, `release.json`;
- поля `release.json` (`schema`, `version`, `tag`, `prerelease`, `assets[].name/size/sha256`, `root`, `entry`). Несумісна зміна формату означає новий `schema`;
- структура архіву: корінна папка `aichat/`, точка входу `dist/broker/main.js`, файл `VERSION`;
- `GET /health` повертає `{"ok":true,"version":"<версія>"}` (`src/version.ts` читає `package.json`);
- протокол запускача (`src/launcher.ts`, `src/updates/layout.ts`): папки `<AICHAT_HOME>/<версія>`, файли `current`, `pending.json`, `failed.json`, код виходу 75 («перезапусти мене»). Запускач живе в Docker-образі й оновлюється рідко, тому нові версії брокера мають працювати зі старим запускачем: протокол лише розширюй, нічого не прибирай.

Нова runtime-залежність має бути чистим JS: архів один для всіх ОС, нативних модулів у ньому бути не може.
Брокер, який стартує, мусить викликати `updater.confirmStartup()` після `listen()`: без цього запускач через 90 с вважатиме оновлення зламаним і відкотить його.
Docker-образ публікується як `ghcr.io/delpher/aichat:<версія>` і `:latest`.

## Адаптери

Спільне в адаптерах лежить у `src/adapters/core/`: чистий `.mjs` лише з імпортами `node:*` і типами в `.d.mts`. Звідти його імпортують `.mjs`-адаптери, TS-адаптери й тести, а `scripts/bundle.mjs` вкладає його в єдиний файл кожного адаптера. Правило, однакове для всіх адаптерів (тип і ім'я файлу, що можна вивантажувати), пиши там, а не копією в адаптері. Тест `channel-bundles` перевіряє, що зібраний адаптер не імпортує нічого, крім `node:*`.

Інструкції моделі складає `core/instructions.mjs`: правила для всіх агентів з брокера (`GET /api/instructions`, редагуються у вебі), хто агент, короткий блок адаптера про свій рантайм і, останнім, локальні правила власника. Як поводитись, пиши в правилах брокера (`src/broker/rules-draft.ts`), а не в тексті адаптера: там лише те, чим рантайм відрізняється (як приходять повідомлення, як звуться інструменти). Без імен учасників.

### Чекліст переходу адаптера на інструменти брокера (`/mcp`)

Перевір усе в тому самому PR, бо інакше старі назви лишаються по одній (AIChat 3930–3937):

1. Адаптер: визначення інструментів прибрані, локальні лише `upload_file` і `get_attachment` (через `core/files.mjs`).
2. Конфіг, який пише майстер менеджера (`src/manager/wizard.ts`): сервер `aichat` → `<broker>/mcp`, токен з файлу, не в конфігу. Старий адаптер із новим конфігом не має лишитися без інструментів.
3. Підказки у вхідних повідомленнях і в інструкціях адаптера: назви нових інструментів.
4. Розділ адаптера в `src/broker/agent-guide.ts` і файли, які пише `install()` (наприклад, `AGENTS.md` агента).
5. Запуск проти старого брокера (без `/mcp`): адаптер стартує й каже про це, а не зависає.
